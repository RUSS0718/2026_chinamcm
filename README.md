## 约定

- `data/raw/` 中的文件视为只读输入；清洗和特征结果写入 `data/processed/`。
- `python -m src.Q1` 是 Q1 V2 的统一入口；Q2 V2 使用 `python -B -m src.Q2 run` 或 `python -B -m src.Q2 batch`，汇总使用 `python -B -m src.Q2.summarize`；Q3 真实入口为 `python -B -m src.Q3`，`src/q2.py` 和 `src/q3.py` 保留为兼容包装。真实流程确定后，每问最终保留一个统一入口。
- `src/_internal/` 只保留第 0 轮共享解析、几何、评价与独立审计；Q1 候选实现位于 `src/Q1/`。
- `outputs/qN/` 只保存可追溯的正式结果。运行日志、缓存和临时中间文件统一放在 `_runtime/`，不提交 Git。
- `paper/qN/` 保存能够进入论文的口径、公式、结果解释和局限；不把未经验证的实验结论写成正式结果。
- `tmp/` 仅用于本地临时文件，阶段 commit 前必须确认没有将其纳入提交。
- `requirements.txt` 当前不代表可复现环境；引入实际依赖后必须同步更新。

## 协作与提交定义

本项目采用“分阶段提交、边建模边写论文”的方式推进。本文中的“提交”专指创建一个 Git commit，不等同于 push、合并或最终发布。

- 草稿先在本地完成，由建模同学复核后再创建阶段 commit。
- 一个阶段 commit 只包含一问的当前材料，不混入无关整理、其他问的变更或本地临时文件。
- 每个 commit 前检查变更范围、运行证据和未解决问题；未运行的内容不得写成“已验证”。
- push 由团队另行确认，Agent 不得因为创建了 commit 就自动 push。

阶段 commit 推荐使用以下格式：

```text
q1(v1): 完成问题分析与模型选择
q1(v2): 完成数据处理与模型建立
q1(v3): 完成结果分析与模型检验
q1(final): 提交问题一论文材料包
project(repro): 完成全部问题复现检查
```

## 阶段状态与复核

阶段材料使用以下状态：

```text
DRAFT → REVIEWING → VERIFIED → FINAL
```

- `DRAFT`：负责人正在编写，不得当作正式结果。
- `REVIEWING`：材料已交给复核人，但尚未通过。
- `VERIFIED`：复核人已检查材料、数字和运行证据，允许创建阶段 commit。
- `FINAL`：负责人已将验收通过的材料纳入论文或最终结果。

每份阶段报告须在开头记录问题编号、当前状态、负责人、复核人、最后更新时间和未解决问题。复核不通过时退回 `DRAFT`，修改后重新复核。

## 分阶段交付内容

### 启动阶段：分工与协作材料（H4 前）

提交团队分工与协作表，至少包含：

- 各问、各模型和代码任务的负责人、复核人和截止时间。
- 两位建模同学的交叉检查方式。
- 软件、编程语言、文件格式、命名方式、共享目录和备份方式。
- 模型失败、代码无法运行或负责人超时时的接手人和触发条件。
- 一名集成负责人，负责三问口径、目录和最终运行顺序的一致性。

### 每一问 V1：问题分析报告

V1 用于确定解题路线，不要求代码全部完成。报告应包含：

- 问题目标、已知数据、所需字段、输入、输出和约束。
- 最终需要产出的结果，以及与前一问的依赖关系。
- 一个主方案和至少一个基线或备选方案，比较适用条件、优缺点和数据可行性。
- 最终模型的选择理由、解题步骤或流程图、备选切换条件。
- 尚未解决的问题、风险和需要补充的证据。

V1 验收标准：不阅读题外口头说明时，复核人仍能说清“为什么做、用什么做、产出什么、失败时怎么切换”。

### 每一问 V2：数据处理与模型报告

V2 用于固定数据和数学口径。报告应包含：

- 原始字段说明，以及缺失值、异常值、重复值、作废记录和负数记录的处理规则。
- 处理前后的行数、列数和排除原因，不得静默删除数据。
- 构造指标的定义、经济或业务含义、方向和单位。
- 模型假设、符号表、可直接用于论文的公式、目标函数和约束。
- 参数来源、取值、随机种子、软件环境、求解方法和算法流程。
- 当前代码入口、实际执行命令、阶段运行结果和已知失败情况。
- 选择主模型而不采用基线或备选模型的证据。

V2 验收标准：复核人能仅依据报告写出论文的“数据处理、模型假设、模型建立”，且报告中声称的阶段结果已有实际运行证据。

### 每一问 V3：结果与检验报告

V3 用于回答题目并建立结果证据链。报告应包含：

- 完整、可编辑的结果表，不能只提供截图或局部样例。
- 题目要求的风险评分、分类、排序、名单、额度、利率或其他最终策略。
- 论文需要的正式图，以及每张图的最终绘图数据表、标题、坐标轴、单位、图形含义和图注。
- 直接回答题目的结论、结果解释和必须进入摘要的关键数字。
- 与模型类型匹配的检验：预测或分类模型检查误差和基线；评价模型检查权重与排序稳定性；优化模型检查可行性和参数扰动；仿真模型检查收敛性和随机误差。
- 合理性、灵敏度、稳健性、局限和改进方向；不适用的检验须说明原因。

V3 验收标准：每个重要结论都有具体数值和结果表支持，不使用没有指标、基线或运行证据的“模型效果较好”。

### 每一问最终版：论文材料包

最终材料包应能直接支持论文写作，包含模型选择、数据处理、可编辑公式、符号表、求解过程、最终结果表、正式图与图注、结果分析、模型检验、优缺点、改进方向、参考文献和资料来源。

每个关键数字必须能追溯到相应的结果表、代码入口和运行输出；不得仅记录在聊天、截图或口头说明中。

### 全部问题完成后：复现材料包

复现不在 H64 才首次执行：每一问在 V2 固定参数和环境，在 V3 完成该问的单独复现，H64 前只负责从头运行和组装。

复现材料包包含完整建模源码、允许保存的原始与处理数据、运行顺序、软件和依赖环境、全部参数与随机种子、最终输出文件和复现说明。不允许公开的数据不得进入公共仓库，仅记录来源、文件名、哈希和获取方式。

## 正式图表约定

- 正式数据图至少导出可编辑的 SVG 或 PDF，并提供 PNG 预览；TIFF 只在论文或赛事要求时保留。

- 每张正式图必须记录结论、数据来源、字段、排除规则、单位、图注和最终尺寸，并完成视觉检查。

## 双建模师与论文手交接规范

本节将“边建模边写论文”落实为可执行的三人协作方式。建模师 A、B 分别承担问题或模型的主责，同时互为交叉复核人；论文手 W 负责论文结构、公式转写、图表编排、结果解释和版本整合。论文手不替代建模师判断模型正确性，建模师也不以口头说明替代可追溯材料。

### 交接总规则

每次交接必须形成阶段包，不得只发送聊天消息、截图或口头结论。阶段包至少包含：

- 阶段报告：目标、输入、输出、假设、未解决问题和当前状态；
- 可直接引用的公式、符号表、参数及单位；
- 完整结果表和绘图数据；
- 代码入口、实际运行命令、软件环境、参数和随机种子；
- 每个关键数字对应的结果文件、代码入口和运行输出；
- 需要论文手确认的问题。

论文手只能把 `VERIFIED` 的数字和结论写成正式结论；`DRAFT` 或 `REVIEWING` 材料只能用于论文草稿和待办清单。

### 论文手的具体工作节奏

1. V1 交接当天完成论文骨架、每问的“目标—方法—输出—结论”表、符号表初稿和待补证据清单。此时只写方法路线，不写模型效果。
2. V2 交接前先根据建模师提供的变量名、指标方向、清洗规则和公式占位写方法章节；V2 交接后用实际参数和运行证据替换占位内容。
3. V3 交接后按“结果表 → 数字核对 → 正式图 → 正文解释 → 摘要数字”的顺序写作。表格与正文冲突时，以复核后的运行输出为准。
4. final 阶段冻结正式数字。任何数字、公式、图表或结论发生变化，都必须说明影响范围，重新执行受影响检验，并退回 `REVIEWING` 重新复核。

### 双建模师交叉复核

主责建模师负责方案、代码和结果生成；另一位建模师负责复跑、检查输入输出、核对公式与代码、判断检验是否适用。论文手负责表达和一致性检查，不负责替建模师补造数据或选择未经讨论的模型。

至少完成以下交叉检查：数据字段和清洗规则、公式与代码、参数和随机种子、结果表与运行输出、单位和精度、图表与正文、三问之间的数据和符号衔接。
